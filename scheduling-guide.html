1 The big picture

The scheduler is a program that reads PropertyMeld work orders ("melds") and books them onto the right tech's calendar automatically.

  • Runs in the cloud It runs by itself every morning — nobody has to push a button. It logs into PropertyMeld as a dedicated scheduler account and schedules the day's work.
  • You improve the rules Your job isn't to run it — it's to make it smarter. When you notice it should do something differently, you tell your Claude, it updates the rule, and the change goes live for everyone.
  • Shared through git All the rules live in one shared place (the pm-scheduling repo). A change you push is automatically used by the cloud and seen by Lee Roy and every other scheduler.
One scheduler, one source of truth. There used to be copies floating around on different computers. Now there's exactly one — the cloud — and one shared rulebook. That's why we never run it "for real" on a personal machine (more on that below).

2 Your daily workflow

Open Claude Code inside the pm-scheduling folder and just talk to it in plain English. A normal session looks like:

  1. Start fresh. Ask Claude to pull the latest so you have everyone's newest rules.
    "Pull the latest, then show me a dry-run preview of the Spokane scheduler."
  2. Preview. Claude runs the scheduler in DRY RUN mode — it shows what it would schedule without changing anything in PropertyMeld.
  3. Spot something to fix? Tell Claude in plain words.
    "Justin shouldn't get jobs on Fridays — make that a rule."
    "Schedule pest treatments before regular repairs."
  4. Re-preview to confirm the change does what you wanted.
  5. Save it for everyone. When you're happy, tell Claude to commit and push. The cloud uses it on the next run, and the team gets it automatically.
    "Looks good — commit and push that change."
You never have to remember commands. Claude does the git pulls, previews, commits and pushes for you. You describe what you want in normal language.

3 Golden rules

✓ Pull first ✓ Preview before trusting ✓ Commit & push to share ✗ Never run LIVE on your PC
DoWhy
Pull the latest at the start of every sessionSo you build on everyone's newest rules, not an old copy.
Always preview (DRY RUN) before committing a rule changeYou see exactly what it will do before it's real.
Commit & push every improvementA change that isn't pushed only helps you — pushing shares it with the whole team + the cloud.
⛔ Never run a scheduler "live / for real" on your own computer. The cloud is the one and only live runner. If you run it live too, the same jobs get scheduled twice and techs get double-booked. On your machine: previews only. Need a real run off-schedule? Ask Claude to trigger it in the cloud instead.

4 The scheduling rulebook

These rules apply to every region. (This is the plain-English version of what's in CLAUDE.md.)

📅 Reserved days — never schedule

Sunday Monday Saturday are off-limits. Work is only booked Tuesday – Friday.

⏰ Business hours

Roughly 8:00 AM – 5:30 PM Pacific. Times are stored with the Pacific time zone so they show correctly for everyone.

🧲 Fill nearest days first, then tidy up

The scheduler books the soonest open day first, then compacts the calendar — pulling later jobs earlier into gaps — so techs aren't sitting idle waiting on scattered appointments. It always leaves about a 30-minute buffer between jobs and never double-books a tech.

🔒 Preference lock

If a work order's title or chat asks for a specific day, time, or date (e.g. "tenant only available Thursday afternoon"), the scheduler honors that and won't move it around.

💬 It reads the chat

The scheduler reads the meld's messages to catch scheduling requests. To avoid thrashing, already-scheduled jobs only react to fresh messages (last ~26 hours); not-yet-scheduled jobs honor requests from the last 30 days.

6 Changing a rule

This is the heart of the collaboration. When something should work differently:

  1. Tell your Claude what you want, in plain English.
  2. Claude updates both the plain-English rule in CLAUDE.md and the actual scheduler so they stay in sync.
  3. You preview to confirm.
  4. Claude commits & pushes — now it's the rule for everyone and the cloud starts using it.

Examples of real rule changes:

"Stop scheduling anything on the 4th of July this year."
"In Spokane, do emergencies the same day even if it means bumping a low-priority job."
"Don't auto-assign anything described as a 'quote' or 'estimate'."

8 Troubleshooting

ProblemFix
Repository not found when cloningYou haven't accepted the repo invite yet (or you're signed into a different GitHub account). Accept the invite at github.com/notifications, then clone again.
Push is rejectedAsk Claude to pull with rebase, then push again — someone else pushed first. Claude handles this automatically.
Preview won't run / login errorMake sure your pm.env has your own PropertyMeld email & password. (It's only for previews; it's never uploaded.)
Not sure if a change is safePreview it (DRY RUN) and/or ask Lee Roy before pushing.
Questions → Lee Roy. When in doubt, preview first and ask. Nothing you do in a preview can change PropertyMeld.
